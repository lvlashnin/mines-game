# Code Review: Mines Game App

Проект имеет отличную архитектуру и логическое разделение на слои (API, Hooks, Components, Store). Использование **Zustand** для глобального состояния и **React Query** для серверного состояния — это современный и правильный подход. Однако, есть несколько критических моментов и мест для улучшения.

## 🚨 Критические ошибки и потенциальные баги

### 1. Повторное срабатывание звуков окончания игры
**Файл:** `src/hooks/useBoard.ts`
```typescript
useEffect(() => {
  if (isGameOver && gameState) {
    if (gameState.status === GAME_STATUS.WON) playWin();
    else if (gameState.status === GAME_STATUS.LOST) playLose();
  }
}, [isGameOver, gameState?.status, playWin, playLose]);
```
**Проблема:** Функции `playWin` и `playLose` берутся из хука `useGameSounds`, который использует `useSound` с зависимостью `soundEnabled: !isMuted`. Если пользователь переключит звук (включит/выключит) **после** окончания игры, ссылки на функции `playWin`/`playLose` обновятся, что приведет к повторному срабатыванию `useEffect`. Звук выигрыша/проигрыша проиграется снова.
**Решение:** Использовать `useRef` для отслеживания того, был ли уже проигран звук для текущей игры (по `gameId`), либо убрать `playWin` и `playLose` из массива зависимостей (используя стабильные ссылки или `eslint-disable-next-line`).

### 2. Полное отсутствие обработки ошибок API
**Файлы:** `src/api/mutations.ts`, `src/hooks/useGameEngine.ts`
**Проблема:** В мутациях (`useCreateGameMutation`, `useRevealCellMutation`, `useCashOutMutation`) нет обработчиков `onError`. Если сервер вернет ошибку (например, недостаточно средств, неверный токен, отвал сети), приложение просто "зависнет" в состоянии загрузки или ничего не произойдет.
**Решение:** Добавить глобальный обработчик ошибок через `toast` (нотификации) или локально в компонентах через `mutation.error` и выводить понятные сообщения пользователю.

### 3. Типизация пропсов и возможный краш
**Файлы:** `src/components/game/GameHistory.tsx`, `src/App.tsx`
**Проблема:** В `App.tsx` вы передаете `history={historyData}`, где `historyData` может быть `undefined` во время загрузки. Однако в интерфейсе `GameHistoryProps` тип указан строго как `history: GameHistoryItem[]`. Хотя конструкция `{history?.length > 0 ? ...}` спасает от краша, это нарушение контракта типов TypeScript.
**Решение:** Исправить тип в `GameHistoryProps` на `history: GameHistoryItem[] | undefined`.

## 🛠 Что лучше усовершенствовать (Архитектура и Рефакторинг)

### 1. Антипаттерн с `useIsMutating`
**Файл:** `src/hooks/useGameEngine.ts`
```typescript
const isCreating = useIsMutating({ mutationKey: ["createGame"] }) > 0;
```
**Проблема:** Использование глобального слушателя мутаций `useIsMutating` для локального UI-состояния — это не лучший подход. Это может привести к багам, если появятся другие компоненты, вызывающие такую же мутацию.
**Решение:** Использовать свойство `isPending` напрямую из объекта мутации.
```typescript
const isCreating = createGame.isPending;
const isRevealing = revealCell.isPending;
const isCashingOut = cashOut.isPending;
```

### 2. Искусственная задержка (Hardcoded Delay) в API слое
**Файл:** `src/api/mutations.ts`
```typescript
await new Promise((resolve) => setTimeout(resolve, 400));
```
**Проблема:** Внутри `useCreateGameMutation` стоит хардкод задержки в 400 мс. Вероятно, это сделано для плавности анимации UI, но API-слой не должен отвечать за UI-задержки.
**Решение:** Убрать `setTimeout` из мутации. Если нужно показать лоадер минимум на 400мс, чтобы избежать "мерцания" (flickering), лучше реализовать это на стороне UI (например, использовать хуки для минимального времени показа скелетона/лоадера).

### 3. Дублирование логики главной кнопки игры (DRY)
**Файлы:** `ControlPanel.tsx` и `MobileGameButton.tsx`
**Проблема:** Логика рендера кнопки (условия для Start Game и Cash Out, стили, обработчики) почти полностью дублируется между десктопной панелью и мобильной кнопкой.
**Решение:** Вынести эту логику в отдельный компонент `MainActionControl` или `GameActionContainer`, который будет принимать пропсы для адаптации под разные экраны, чтобы избежать дублирования.

### 4. Оптимизация рендеринга ячеек
**Файлы:** `src/components/game/Board.tsx`
**Проблема:** При любом изменении стейта (например, изменился `betAmount` или `isProcessing`), все 25 ячеек сетки перерисовываются. 
**Решение:** Обернуть компонент `<Cell />` в `React.memo` (или `memo` из React 19). Это незначительно для сетки 5x5, но является хорошей практикой.

### 5. Безопасность математических операций
**Файл:** `src/hooks/useGameEngine.ts`
При вычислении профита используется обычная математика: `activeGame.betAmount * activeGame.currentMultiplier`. В JavaScript работа с числами с плавающей точкой может приводить к ошибкам (например, `0.1 + 0.2 = 0.30000000000000004`). Везде, где есть работа с деньгами (`balance`, `betAmount`), стоит быть осторожным и использовать округление перед отправкой на сервер или рендером.
